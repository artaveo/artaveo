دو نفر یک سفر را باز می‌کنند و روی یک صندلی می‌زنند. روی هر دو صفحه صندلی خالی است و هر دو دربارهٔ چیزی که می‌بینند درست می‌گویند، اما فقط یکی از آن‌ها می‌تواند صاحب صندلی شود. این یادداشت دربارهٔ این است که چنین تصمیمی کجا باید گرفته شود و من در Transportation System، پروژهٔ شخصی رزرو بلیت بین‌شهری‌ام، چه کردم.

> [!NOTE] دامنهٔ این یادداشت
> همه‌چیز اینجا دربارهٔ هستهٔ رزرو است: صندلی، رزرو موقت و تأیید نهایی. این پروژه هنوز به درگاه پرداخت واقعی وصل نیست، پس این یادداشت دربارهٔ پرداخت نیست.

## مرورگر می‌تواند بپرسد، تصمیم با پایگاه داده است

نقشهٔ صندلی در مرورگر تصویری است از پایگاه داده در لحظه‌ای که صفحه باز شد. تا کاربر روی صندلی بزند، این تصویر می‌تواند چند ثانیه قدیمی شده باشد. اگر مرورگر بپرسد «هنوز خالی است؟» و بعد رزرو کند، عملاً با نفر بعدی که همین کار را می‌کند مسابقه داده است.

برای همین مرورگر هیچ‌وقت تصمیم نمی‌گیرد. از سرور می‌خواهد صندلی‌ها را نگه دارد، سرور این کار را به یک تابع Postgres می‌سپارد و جواب یکی از دو حالت است: انجام شد، یا نشد.

```ts
const supabase = createServiceClient()
const { data, error } = await supabase.rpc("hold_seats", {
  p_trip_id: tripId,
  p_seat_ids: seatIds,
  p_hold_minutes: HOLD_MINUTES,
})

if (error) {
  if (error.message.includes("SEATS_UNAVAILABLE")) {
    return NextResponse.json({ error: "SEATS_UNAVAILABLE" }, { status: 409 })
  }
  console.error("[api/bookings/hold]", error.message)
  return NextResponse.json({ error: "UNKNOWN" }, { status: 500 })
}
```

این بخشی از Route Handler است و تنها دروازه است. تابع را با کلاینت service role صدا می‌زند که فقط روی سرور وجود دارد و هرگز از یک Client Component صدا زده نمی‌شود. درخواست هم پیش از رسیدن به تابع بررسی می‌شود: تعداد صندلی‌ها فقط در رابط کاربری نیست، روی سرور هم حداکثر شش است.

## صندلی سه حالت دارد و یک مهلت

هر صندلیِ هر سفر یک ردیف است. جز «خالی» و «رزروشده» یک حالت میانی هم دارد، «نگه‌داشته‌شده» (held)، و همراهش زمانی که مهلت نگه‌داشتنش تمام می‌شود. یک قید یکتا هم جلوی این را می‌گیرد که یک سفر برای یک شمارهٔ صندلی دو ردیف داشته باشد.

```sql
create type seat_status as enum ('available', 'held', 'booked');

create table trip_seats (
  id uuid primary key default gen_random_uuid(),
  trip_id uuid not null references trips(id) on delete cascade,
  seat_number text not null,
  row_number int not null,
  col_label text not null,
  status seat_status not null default 'available',
  held_until timestamptz,
  created_at timestamptz not null default now(),
  constraint trip_seats_unique_per_trip unique (trip_id, seat_number)
);
```

## یک دستور، همه یا هیچ

تابع `hold_seats` یک `UPDATE` واحد است که فقط از میان صندلی‌های درخواستی آن‌هایی را عوض می‌کند که هنوز خالی‌اند یا مهلت نگه‌داشتنشان تمام شده. بعد تعداد ردیف‌هایی را که واقعاً به‌روز شده‌اند با تعداد صندلی‌های درخواستی مقایسه می‌کند. اگر برابر نباشند، خطای `SEATS_UNAVAILABLE` می‌دهد و Postgres کل عملیات را برمی‌گرداند؛ اگر برابر باشند، صندلی‌ها را برمی‌گرداند.

از این دو نتیجه می‌گیرم که برایم مهم‌اند. دو درخواست برای یک صندلی نمی‌توانند هر دو موفق شوند. و درخواستی برای سه صندلی که یکی‌اش همین حالا گرفته شده، هیچ‌کدام را نمی‌گیرد، نه فقط دو تا را.

راه دیگری که کنار گذاشتم انجام همین کار از جاوااسکریپت است: صندلی‌ها را بخوان، بررسی کن، بنویس. این سه قدم جداست و درخواست دیگری می‌تواند بین هر دو قدمش وارد شود. داخل یک دستور، «بین» وجود ندارد.

وقتی تابع رد می‌کند، Route Handler خطای `SEATS_UNAVAILABLE` را به پاسخ ۴۰۹ تبدیل می‌کند و مسافر پیامی روشن می‌بیند، نه موفقیتی که درست نیست.

## رزرو موقت بدون کار پس‌زمینه منقضی می‌شود

مهلت نگه‌داشتن ده دقیقه است. صندلی‌ای که هنوز «نگه‌داشته‌شده» ثبت است ولی مهلتش گذشته، در سه جا خالی حساب می‌شود: نقشهٔ صندلی، شمارش صندلی‌های باقی‌مانده، و خود `hold_seats`. برای آزاد شدنش لازم نیست چیزی زمان‌بندی‌شده اجرا شود. وقتی مسافر صفحهٔ پرداخت را ترک می‌کند هم تابع `release_seats` صندلی‌ها را فوراً آزاد می‌کند.

هزینه‌اش صادقانه و کوچک است: چون کار پاک‌سازی زمان‌بندی‌شده‌ای نیست، ردیف‌های منقضی تا وقتی چیزی به آن‌ها دست نزند «نگه‌داشته‌شده» می‌مانند، پس مدیر نمی‌تواند تعداد دقیق صندلی‌های نگه‌داشته‌شدهٔ همین لحظه را مستقیم از جدول بخواند. اگر روزی این عدد مهم شد، قدم بعدی یک کار پاک‌سازی واقعی است.

## دسترسی‌ای که فقط در مستندات بود

در گزارش آن فاز نوشته شده بود که سه تابع `hold_seats`، `release_seats` و `confirm_booking` از نقش‌های `anon` و `authenticated` گرفته شده و فقط به `service_role` داده شده‌اند. بررسی مستقیم دسترسی تابع‌ها روی پروژهٔ زندهٔ Supabase (`pg_proc.proacl`) در فاز بعد نشان داد این revoke هرگز اجرا نشده بود.

یعنی هر کسی با کلید عمومی anon، که به‌طور طبیعی در مرورگر است، می‌توانست این توابع را مستقیم از REST API عمومی Supabase صدا بزند و همهٔ بررسی‌های Route Handler را دور بزند. درستش کردم:

```sql
revoke execute on function public.hold_seats(uuid, uuid[], integer) from public, anon, authenticated;
grant execute on function public.hold_seats(uuid, uuid[], integer) to service_role;
```

همین دو دستور برای `release_seats` و `confirm_booking` هم نوشته شد. درسش کوچک و عملی است: «دسترسی بسته است» در یک سند، بسته بودن دسترسی نیست. از خود پایگاه داده بپرس.

## حالا در هر سامانهٔ رزرو چه چیزهایی را بررسی می‌کنم

- مالکیت صندلی را چه کسی تعیین می‌کند؟ باید پایگاه داده باشد، نه صفحه.
- آیا گرفتن صندلی و بررسی خالی بودنش یک عملیات اتمیک است؟
- آیا هر رزرو موقت مهلت دارد، و بعد از مهلت چه چیزی پاک‌سازی می‌کند؟
- روی پایگاه دادهٔ زنده، چه کسی می‌تواند تابع را صدا بزند؟ نه آنچه مستندات می‌گویند.
- آیا دو تب مرورگر روی یک صندلی در یک لحظه، یک رد روشن می‌گیرند؟

بررسی آخر ابزار نمی‌خواهد: یک سفر را در دو تب باز کن، در هر دو یک صندلی را انتخاب کن و همزمان ادامه را بزن. دقیقاً یکی از آن‌ها باید بشنود که صندلی رفته است.
